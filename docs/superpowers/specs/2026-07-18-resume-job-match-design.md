# 多版本简历岗位匹配设计

## 目标

为同一登录用户提供“从多个已上传简历版本中，按目标岗位 JD 选择最适合投递版本”的能力。岗位匹配不修改简历；用户选择推荐结果后，再跳转到既有简历优化流程。

## 范围与约束

- 新增独立前端页面和侧边栏入口：`岗位匹配`，位于“简历优化”下方、“AI 面试”上方。
- 用户必须显式勾选至少一份已解析完成的简历；不默认使用账号下全部简历。
- 仅允许操作当前登录用户拥有的简历。提交的所有 `resumeIds` 必须存在、归属当前用户且已完成解析。
- 一次任务最多选择 20 份简历，JD 继续复用现有长度限制。
- 结果按推荐度排序，显示文件名、解析时间、匹配分数、匹配等级、命中点和主要缺口。
- 点击“用这份简历去优化”时，携带 `resumeId` 与 JD 跳转至现有简历优化页面。
- 所有任务继续记录在 `career_job_match_task`，支持查询当前用户最近的任务历史。

## 后端设计

### 请求与校验

将岗位匹配请求扩展为：

```json
{
  "jobDescription": "岗位 JD",
  "resumeIds": [101, 102, 103],
  "limit": 3
}
```

服务端在创建任务前校验 `resumeIds` 非空、无重复、数量不超过 20，并验证每份简历属于当前用户且解析完成。校验失败不会创建匹配任务。

### 匹配与结果

对勾选简历确保 embedding 已生成，再在该 `resumeIds` 范围内执行现有 RAG 检索。检索结果转换为结构化候选项，至少包含简历标识、文件名、排序、分数/等级、命中点和缺口。若 RAG 或 rerank 不可用，任务返回明确 `FAILED` 状态与可诊断错误信息；不返回其他用户或未勾选简历。

### 历史

保留任务表作为事实记录。新增当前用户的最近任务历史读取接口，返回任务输入 JD、选中的简历数量、状态、结果摘要、失败原因和创建时间。

## 前端设计

页面为两栏：左侧选择已解析完成的简历，右侧输入 JD 和展示结果。未选简历或未填写 JD 时禁用“开始匹配”。匹配成功按推荐度显示 Top N 卡片；点击卡片操作会进入简历优化，并自动回填对应简历和 JD。页面提供最近匹配历史，恢复历史时只读取当前账号的数据。

## 错误与安全

- 不允许空选择、跨用户简历、未解析简历或重复简历 ID。
- 当前账号切换时清空页面暂存和轮询，避免缓存串号。
- API 返回失败时保留用户已选简历与 JD，展示可重试原因。
- 匹配结果不依赖前端传回的文件名或用户 ID，全部由服务端按已验证简历 ID 查询。

## 验收与测试

1. 同一用户勾选多份简历，按 JD 返回有序结构化结果。
2. 未勾选、勾选他人简历、勾选未完成解析简历时，服务端拒绝请求且不创建任务。
3. 未勾选的本人简历不出现在检索范围或结果中。
4. 匹配成功、失败分别正确写入 `career_job_match_task`。
5. 前端可选择、匹配、查看历史，并可带参数跳到简历优化。
6. 用户切换后不会读取或展示另一账号的匹配历史/缓存。
